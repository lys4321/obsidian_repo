쿠버네티스란
- 컨테이너화 된 애플라케이션을 관리하는 오픈소스 플랫폼
- 컨테이너 오케스트레이션 도구

-----
특징
- 서비스 디스커버리와 로드 밸런싱
	- DNS 명이나 자체 IP를 사용해 컨테이너를 노출(디스커버리)
	- 트래픽이 많으면 로드밸런싱 후 배포해 안정적으로 이뤄지게함
- 스토리지 오케스트레이션
	- 저장소 시스템을 자동 탑재
- 자동화된 롤아웃과 롤백
	- 컨테이너 상태를 변경을 이용해 컨테이너 배치 가능
- 자동화된 빈 패킹
	- 사용 리소스를 설정할 수 있는 클러스터 노드를 제공
- 자동화된 복구
	- 실패한 컨테이너에 대한 교체를 자동으로 실행
- 시크릿과 구성관리
	- 컨테이너 이미지를 재구성 하지 않고 시크릿, 애플레이션 구성을 배포 및 업데이트
- 배치 실행
	- 배치, CI 워크로드를 관리하여 실패한 컨테이너에 대한 교체
- 수평 확장
	- 명령어나 자원 사용량에 따라 자동으로 애플리케이션 확장/축소
- 확장성을 고려한 설계
	- 업스트림 소스 코드를 변경하지 않고 클러스터 기능을 추가

컴포넌트
크게 Control Plane과 1개 이상의 Wokrer Node로 구성
- Control Plane
	- CCM(Cloud Controller Manager) 
		- 기본 클라우드 공급자와 통합
	- CM(kube-controller-manager)
		- 컨트롤러를 실행해 k8s API 동작을 구현
	- etcd(persistence store)
		- 모든 API 서버 데이터를 위한 일관성, 고가용성 기능을 갖춘 키-값 저장소
	- api(kube-apiserver)
		- k8s HTTP API를 노출하는 서버 컴포넌트 
	- sched(kube-scheduler)
		- 아직 노드에 할당하지 않은 파드를 찾아 노드에 할당
- Woker Node
	- kubelet 
		- 파드와 그 안의 컨테이너가 실행 중임을 보장
		- CRI를 호출해 컨테이너 런타임 생성
	- kube-proxy
		- 노드에서 네트워크 규칙을 유지하여 서비수 구현
	- 컨테이너 런타임
		- 컨테이너 실행을 담당하는 SW
		- CRI의 구현체

추가적인 구성요소
- 애드온 
	- DNS 
		- 클러스터 전반의 DNS 해석 담당
	- 웹 UI (대시보드)
		- 웹 인터페이스를 통한 클러스터 관리 제공
	- 컨테이너 리소스 모니터링
		- 컨테이너 매트릭을 수집, 저장
	- 클러스터-레벨 로킹
		- 컨테이너 로그를 중앙 로그 저장소에 저장

오브젝트

쿠버네티스 API
- 쿠버네티스 API란?
	- kube-apiserver에게 보내는 k8s 오브젝트 상태를 쿼리하고 조작하기 위한 요청
- 사용하는 이유
	- 모든 명령, 상태조회, 리소스 생성은 kube-apiserver를 통해 이뤄지기 때문에 원하는 요청을 보내기 위하여 사용
	- API는 RESTful 구조로 설게되어 HTTP 요청으로 리소스를 CRUD 가능
- API의 구조와 버전
	- k8s API 는 여러 그룹으로 나눠짐
		- core/v1(기본그룹)
		- batch/v1
		- `rbac.authorization.k8s.io/v1` 등
	- 그룹과 버전을 통해 API 경로가 정해진다.(예 : /api/v1, api/v2)
	- 서로 다른 버전이 동일한 리소스의 표현을 제공
		- '서로 다른 버전이 동일한 리소스의 표현' 이란
			- 같은 리소스(예 : Deployment)라도 여러 API 버전(예 : apps/v1beta1, apps/v1) 을 제공
	- API 안정성 수준
		- 안정(stable) : 안정된, 장기 호환성 보장하는 버전
		- 베타(Beta) : 실험적/새기능이 포함된 버전
		- 알파(Alpha) : 심화적으로 실험적인, 진짜 완전 실험적
- 데이터 저장과 직렬화
	- k8s는 오브젝트 상태를 etcd에 저장하는데 API 서버가 여기를 읽고 쓰는 중앙 허브 역할함
	- API 오브젝트는 OpenAPI 스펙을 통해 정의 됨
	- 내부적으론 Protobuf 직렬화 형식을 사용해 클러스터 내부 통신을 효율화
- API 확장성
	- 커스텀 리소스(Custom Resource Definition, CRD)를 통해 사용자 정의 API 타입을 k8s 클러스터에 추가 가능
	- API 애그리게이션(Aggregated API)레이어를 사용해 별도의 API 서버를 연결 가능
- API 접근과 보안
	- API를 사용하기 위해서는 인증과 인가를 거쳐야함
	- k8s는 여러 클라이언트 라이브러리를 제공
	- 파드 내부에서도 API에 접근이 가능(파드 내에서 클러스터 정보를 읽거나 조작할 때 유용)

클러스터 아키텍처
개요
- 클러스터란 k8s를 구성하는 기본 단위로, 여러 노드와 컨트롤 플레인으로 구성됨
- 이것의 목적은 컨테이너화된 애플리케이션을 안정적으로 배포 스케일, 관리하는 것
- 구성 요소
	- 컨트롤 플레인(Control Plane)
		- 클러스터를 관리하고 의도한 상태를 유지하는 중심 컴포넌트
		- kube-apiserver
			- 클러스터의 중앙허브 역할을 담당하고 모든 REST API 요청을 처리
			- 상태를 etcd에 저장하고 인증, 권한 검사를 수행
		- etcd
			- 분산 키-값 저장소이며, 클러스터 상태(오브젝트 상태)를 저장
			- API 서버는 etcd에서 데이터를 읽고 쓰며, 내부 모델 기준으로 버전을 변환
		- kube-scheduler
			- 새로 생성된 파드를 적절한 노드에 배치
			- 리소스 요구량, 정책, affinity/anti-affinity 등 고려
		- kube-controller-manager 
			- 다양한 컨트롤러 실행
			- 예시로 ReplicaSet, Deployment, Node Controller 등 
			- 선언적 상태(desired state)와 실제 상태(actual state)를 맞추는 담당
		- cloud-controller-manager
			- 클라우드 인프라와 연동
			- 노드 상태, 로드밸런서, 볼륨 등을 관리
	- 노드(Node)
		- 애플리케이션이 실제 실행되는 서버 단위
		- kubelet
			- 노드에서 실행되는 에이전트
			- 파드가 정상 실행이 되는지 감시하고 상태를 API 서버에 보고
		- kube-proxy
			- 네트워크 프록시 및 로드밸런싱
			- Service IP와 파드 간 연결 유지
		- 컨테이너 런타임(Container Runtime)
			- 실제 컨테이너를 실행하는 엔진
			- 예 : 도커, containerd, CRI-O
- 클러스터 동작 개념
	- 사용자가 Deployment 생성 요청 -> kube-apiserver
	- API 서버가 상태를 etcd에 기록
	- kube-scheduler가 파드를 노드에 배치
	- kubelet이 노드에서 파드를 실행하고 상태를 보고
	- 컨트롤러 매니저가 실제 상태와 의도한 상태를 비교해서 부족한 파드를 생성하거나 삭제
		- 이 과정에서 Desired State와 Self-healing 개념이 중요

노드
- 노드 란?
	- k8s에서 실제 애플리케이션이 실행되는 곳을 의미
	- 물리 서버, 가상머신 모두 가능
	- 하나의 클러스터에는 여러 노드가 존재 가능하며, 각 노드는 컨테이너화 된 애플리케이션(Pod)을 호스팅
- 노드의 구성 요소
	- kubelet
		- 노드에 항상 실행되는 에이전트
		- 기능
			- 노드에서 Pod가 정상적으로 실행하는지 감시
			- Pod 상태를 API 서버에 보고
			- Pod 스펙에 따라 컨테이너 런타임에 명령 전달
	- 컨테이너 런타임(Container Runtime)
		- 실제 컨테이너를 실행하는 엔진
		- 도커, containerd, CRI-O 등
		- kubelet 이 Pod 스펙을 바탕으로 컨테이너를 관리
	- kube-proxy
		- 네트워킹 및 서비스 라우팅 담당
		- 기능
			- Service IP를 Pod와 연결
			- 로드밸런싱 수행
			- 클러스터 내/외부 트래픽 관리
- 노드 역할 및 기능
	- Pod 실행 : 워커 노드는 컨트롤 플레인에서 스케줄된 Pod를 실행
	- 상태 보고 : kubelet이 Pod와 노드 상태를 API 서버에 주기적으로 보고
	- 네트워크 관리 : kebe-proxy를 통해 Service와 Pod 간 통신 제공
	- 리소스 관리 : 리소스 모니터링 및 컨테이너 할당
컨트롤 플레인 - 노드 간 통신
- k8s 클러스터에선 컨트롤 플레인과 노드 사이에선 지속적인 통신이 이뤄짐
- 목적
	- 컨트롤 플레인이 클러스터 상태를 관리
	- 노드가 Pod 실행 상태를 보고
	- 리소스 상태, 이벤트, 네트워크 정보 등을 전달
- 통신 방향
	- 노드->컨트롤 플레인
		- kubelet이 주도
		- 기능
			- 노드 및 Pod 상태를 컨트롤 플레인에 주기적으로 보고
			- 컨테이너 상태, 이벤트, 노드 리소스 사용량을 전달
			- 컨트롤 플레인에게 Desired State와 Actual State를 비교한 정보를 제공
		- 통신 방식
			- HTTPS 요청을 통해 kube-apiserver와 통신
			- API 서버 인증 및 인가 검사를 거침
	- 컨트롤 플레인->노드
		- 컨트롤 플레인이 주도
		- 기능
			- kube-scheduler가 스케줄링한 Pod 실행 명령을 전달
			- 컨트롤러 매니저가 Pod 관리 명령을 전달
		- 통신 방식
			- API 서버를 통한 kubelet과의 간접 통신
- 통신 구성 요소
	- kubelet : 노드에서 Pod 실행 및 상태를 보고
	- kube-proxy : 네트워크 트래픽 관리, 서비스 라우팅
	- kube-apiserver : 중앙 허브, 모든 요청에 대한 처리 및 상태 기록
		- 통신은 TLS 기반, 인증 및 RBAC 권한 확인 후 처리
	- etcd : 클러스터 상태 저장소
	- Controller Manager : 상태 비교 및 조치 수행
	- Scheduler : 새 Pod 배치 결정
리스(Lease)
- Lease 란?
	- k8s 에서 리소스 상태 유지와 주기적 갱신(heartbeat) 정보를 관리하기 위한 API 오브젝트
	- 주로 Node Lease 형태로 사용되며 노드의 생존상태(node heartbeat) 를 추적하는 용도로 사용
		=> Lease는 컨트롤 플레인이 노드가 살아있는지 확인하는 경량 오브젝트
- 구조
	- Metadata
		- 이름(metadata.name), 네임스페이스(metadata.namespace)
		- Node Lease는 보통 kube-node-lease 네임스페이스에 존재
	- Spec
		- Lease 정보와 갱신 관련 데이터
		- 대표 예시
			- holderIdentity : Lease를 소요한 객체 이름(노드명)
			  leaseDurationSeconds : Lease 유효 기간
			- acquireTime/renewTime : Lease 획득 및 갱신 시간
- 사용 목적
	- node heartbeat 관리
		- kubelet이 주기적으로 갱신
		- 컨트롤 플레인은 갱신 시간을 보고 노드의 생존여부 파악
	- 클러스터 성능 최적화
		- 기존 node status 보다 가볍고 효율적
		- node 상태 확인에 발생하는 etcd 쓰기 부담이 감소
컨트롤러
- k8s에서 클러스터의 현재 상태를 원하는 상태로 유지시키는 자동화 루프 => Desired State와 Current State 를 지속적으로 비교하고 차이가 있을 시 자동으로 조정(Reconcile)
- 특징
	- 이벤트 + 루프 기반
		- Watch 이벤트로 API 오브젝트 변경을 감지
		- 지속적으로 루프를 돌며 상태가 원하는 상태인지 감시
	- 컨트롤러는 여러개가 쓰이며 서로 다른 레벨에서 역할을 분담
	- 컨트롤러는 리소스를 '직접 조작'하지 않는다
	- k8s는 원하는 상태만 선언하면 자동 관리가 된다는 선언적 API 모델을 가지는데, 이 모델에 컨트롤러가 사용됨
	- API 오브젝트를 관찰하며 그 오브젝트가 정의한 목표 상태를 만족하기 위해 행동
- 동작 원리
	- 현재 상태 관찰 
	- 원하는 상태(Spec)와의 비교
	- 조치 실행
	- 다시 반복(ReconcileLoop\==조정 루프)
- 범주의 종류
	- 빌트인 컨트롤러(kube-controller-manager 내부)
		- 대부분의 주요 기능이 빌트인 컨트롤러로 동작
			- Deployment
			- ReplicaSet
			- Job
			- Node
			- EndpointSlice
			- Namespace
			- Service
	- CRD 기반의 커스텀 컨트롤러
		- 사용자가 정의한 '새로운 리소스 종류(CRD)'을 실제로 조정하는 로직을 '커스텀 컨트롤러(Operator)'로 구현
- 컨트롤러의 종류
	- Deployment Controller
		- ReplicaSet 관리
	- Replica Controller
		- Pod 개수 조정
	- Job Controller 
		- 일정 횟수의 Pod 실행/완료 보장
	- Node Controller
		- 노드 상태 감지, 노드 장애 시 조치
	- Service Controller
		- 클라우드 로드밸런서 등 외부 리소스 생성
	- Namespace Controller
		- 삭제된 네임스페이스 내 리소스 정리

클라우드 컨트롤러 매니저(CCM)
- CCM는 k8s의 control-plane 구성요소 중 하나로 클라우드 공급자(Cloud Provider)의 API와 클러스터 연결해주는 역할 담당
- 클라우드 플랫폼과 상호 작용하는 구성요소 (cloud-specific control logic)를 포함하며, 클라우드 인프라와 통신하는 부분과 클러스터 내부와 통신하는 것을 분리하는 구성을 가짐
	- 이 구성으로 인하여 k8s 본체 프로젝트의 속도와는 상관없이 별개의 속도로 기능을 릴리스
- CCM이 구현하는 주요 컨트롤러 기능
	- Node Controller(Node lifecycle controller)
		- 클라우드 인프라에서 새 서버가 생성되면 Cloud Provider API에서 고유 식별자를 받아와 k8s의 Node 객체에 기록
		- 클라우드 관련 정보를 사용해서 노드 오브젝트에 어노테이션과 레이블 작성
		- 노드의 호스트 이름과 네트워크 주소를 가져옴
		- 노드의 상태를 확인하여 응답하지 않는 경우 이 컨트롤러는 Cloud Provider API를 통해 서버의 상태를 확인하여 노드가 클라우드에서 삭제된 경우 사용자의 k8s 클러스터에서 노드 오브젝트를 삭제
	- Route Controller
		- 클러스터 내 서로 다른 노드에 있는 컨테이너들이 통신할 수 있도록 클라우드 쪽에서 네트워크 라우트를 설정해야함
		- Cloud Provider에 따라서 Pod 네트워크를 위한 IP 블록을 할당할 수도 있다
	- Service Controller
		- 서비스는 클라우드 인프라의 관리형 로드밸런서, IP주소, 네트워크 패킷 필터링, 대상 상태 확인과 같은 클라우드 인프라스트럭쳐 컴포넌트와 통합됨
			=> 서비스 컨트롤러는 사용자의 Cloud Provider API와 상호 작용하여 서비스 리소스를 선언 시, 클라우드에서 로드밸런서를 생성하거나 설정하는 작업을 처리
- 권한 인가
	- Node Controller
		- v1/Node 객체에 대해 get, list, create, update, patch, watch, delete 권한이 필요
	- Route Controller
		- v1/Node 객체에 대해 get 권한이 필요
	- Service Controller
		- v1/Service 객체에 대해 list, get, watch, patch, update 권한이 필요
	- 기타
		- v1/Event 객체에 대해 create, patch, update 권한이 필요
		- v1/ServiceAccount 객체에 대해 create 권한 필요
cgroup
- 개념 및 필요성
	- 리눅스에서 control cgroup은 프로세스에게 할당된 리소스를 제한하는 기술
	- k8s의 kubelet과 컨테이너 런타인은 cgroup과 상호작용하여 Pod, 컨테이너에 대한 리소스를 제한할 수 있다.
	- 리눅스에는 cgroup v1과v2가 있으며 k8s cgroup v2는 새 버전의 cgroup API 이다.
- cgroup v2란?
	- '통합된 제어 시스템(unified controle system)'을 제공하며 기존보다 리소스 관리 기능이 향상된 버전
	- 개선 및 변경점
		- v1에서 stable(안정) 상태는 v2에서 FEATURE STATE(기능 상태)로 변경됨
		- API 계정구조가 단일화
		- 컨테이너에 대한 서브트리 위임기능이 안정됨
		- PSI(Pressure Stall Information) 기능 추가
		- 리소스 간 리소스 할당 및 격리 향상
		- 
자가치유(Self-Healing)
- 시스템이 Desired State를 유지하도록 보장하는 기능이며 이로인하여 워크로드의 상태와 가용성이 유지
- 주요 기능
	- 컨테이너 단위 재시작
		- Pod 안의 컨테이너가 실패하면 재시작 정책(restartPolicy)에 따라 자동으로 재시작
	- 레플리카(Replica) 교체
		- Deployment, StatefulSet의 Pod가 실패 시, 지정 Replica 수를 유지하기 위해 대체 Pod를 생성
		- DeamonSet의 일부인 Pod가 실패 시, Control-Plane이 대체 Pod를 생성하여 동일 노드에 다시 연결
	- Persistance Storage(영구 스토리지) 복구
		- Persistance Volume이 연결된 파드를 실행 중일 때 노드에 장애가 발생하면 k8s는 다른 노드에 있는 새 Pod에 재연결
	- Service Load Balancing
		- Service 뒤에 있는(연결된) Pod 장애 시, k8s는 자동으로 Service의 Endpoint에서 해당 Pod를 제거해 정상 Pod로만 트래픽을 라우팅
- k8s에서 자가 치유를 제공하는 컴포넌트
	- kubelet
		- 컨테이너가 실행 중인지 확인 후, 실패한 컨테이너를 재시작
	- ReplicaSet, StatefulSet, DeamonSet의 컨트롤러
		- Pod Replic를 원하는 수로 유지
	- Persistance Volume 컨트롤러
		- 상태 저장 워크로드에서 volume 연결에 대하여 연결 및 해제를 관리
컨테이너 런타임 인터페이스(CRI)
- CRI는 플러그인 인터페이스로 kubelet이 다양한 컨테이너  런타임을 사용하게 돕는다
	=> 이를 통해 클러스터 컴포넌트를 다시 컴파일 없이 런타임 변경하게 한다.
- 모든 노드에는 컨테이너 런타임이 있어야하며 kubelet은 이를 사용해 Pod와 컨테이너를 실행
- CRI는 kubelet과 컨테이너 런타임 간 통신을 위한 프로토콜
- k8s의 CRI는 gRPC기반 프로토콜을 정의

가비지(Garbage) 수집
- k8s가 클러스터 자원을 정리하기 위해 사용하는 여러 기술을 아우르는 용어
	- 종료된 Job
	- 소유자가 없는 오브젝트(dangling 오브젝트)
	- 사용되지 않는 컨테이너 및 컨테이너 이미지
	- 반환 정책이 삭제인 스토리지 클래스에 의해 동적으로 생성된 Persistance Volume
	- Stale 또는 만료된 certificateSigningRequests(CSR)
	- 클러스터가 CCM을 사용하는 클라우드인 경우 노드가 삭제
	- 클러스터가 CCM과 유사한 애드온을 사용하는 온프레미스인 경우 노드가 삭제
	- 노드 Lease 오브젝트
- 소유자와 종속 객체 규칙
	- 소유자와 종속자는 동일 네임스페이스에 있어야한다.
	- 소유자와 종속자는 동일 클러스터에 있어야한다.
- 캐스케이딩 삭제(Cascading Deletion)
	- 포그라운드 캐스케이딩 삭제
		- 소유자가 먼저 삭제중으로 표시되고 metadata.deletionTimestamp가 설정됨
		- API서버는 metadata,finalizers필드에 forgroundDeletion 을 설정
		- 소유자가 실제 API에서 조회되는 동안 컨트롤러가 먼저 모든 종속자를 삭제
		- 종속자가 삭제된 후 컨트롤러가 소유자를 최종삭제
		- 만약 ownerReference.blockOwnerDeletion=true일 시, 종속자는 소유자 삭제를 막을 수 있다.
	- 백그라운드 캐스케이딩 삭제
		- API 서버는 소유자를 즉시 삭제하고 그 다음 백그라운드에서 컨트롤러가 종속자를 한다.
	- 분리된 종속 객체
		- 소유자 삭제 시 종속자가 남을 수 있는데 이걸 분리된(deorphaned) 종속 객체라 부르는데 k8s에서는 기본적으로 이런 분리된 종속자도 삭제하는 방법을 사용한다.
		- 만약 이 동작을 오버라이드해서 분리된 종속자를 남기도록 설정할 수 있다.
- 사용되지 않는 컨테이너 및 이미지의 가비지 수집
	- kubelet은 주기적으로 컨테이너는 1분, 이미지는 5분마다 미사용 여부를 조회해 정리한다.
	- 이미지 라이프사이클
		- kubelet의 이미지 매니저와 cAdvisor가 협력해 이미지의 라이프사이클을 관리
		- 가비지 수집 시 디스크 사용량을 제한
			- HighThresholdPercent, LowThresholdPercent 설정 사용됨
			- HighThresholdPercent에 설정된 것보다 초과 시 가장 오래된 이미지부터 삭제를 시작하여 LowThresholdPercent 수준까지 삭제를 마무리한다.
- 컨테이너에 대한 가비지 수집 세부 설정
	- kubelet은 변수를 통해 사용자가 가비지 수집 동작을 조절하게 함
		- MinAge : 가비지로 수집할 수 있는 최소 나이 설정, 0 이면 비활성화
		- MaxPerPodContainer : 각 Pod 쌍이 가질 수 있는 죽은 컨테이너의 최대 수, 0이면 비활성화
		- MaxContainers : 죽은 컨테이너의 최대 수, 0 이면 비활성화
	- 설정 간에 충돌이 발생할 수 있으나 kubelet이 설정값들을 조정해 문제를 해결하게 한다.
- 가비지 수집 구성
	- 가비지 수집 동작은 컨트롤러의 옵션이나 kubelet 설정파일에서 조정
Mixed Version Proxy
- API 서버가 동일 클러스터 내 다른 API 서버로 요청을 프록시하게 하는 기능
- 다른 버전의 k8s API 서버들이 사용중일 때 유용
	=> 안정성 높은 클러스터 업그레이드를 가능하게하는 기술
- 기능 활성화 방법
	- API 서버의 UnknownVersionInteroperabilityProxy 라는 Feature-gate 를 켜야함
	- API 서버 간 상호 인증(inter-API-server authentication)을 위한 여러 인증 관련 플래그가 사용됨
		- --peer-ca-file : 동료 API 서버의 CA인중서 지정
		- --proxy-client-cert-file, --proxy-client-key-file : 출발 API 서버가 자신의 신원을 증명하기 위한 클라이언트 인증서와 키
		- --requestheader-client-ca-file : 도착 API 서버가 proxy-client 인증서를 검증 시 사용할 CA 인증서를 지정
		- --requestheader-allowed-names : proxy-client 인증서의 Common Name(CN)을 검증하기 위한 이름 목록
	- 네트워크 위치 설정
		- --peer-adverties-ip, --peer-adverties-port : 플래그를 사용하여 동료 API 서버가 proxy 대상으로 사용할 IP와 포트를 지정. 만약 설정되지 않으면 기본적으로 --adverties-address나 --bind-address 값이 사용된다.
	- 프록시 동작 방식
		- Mixed Version Proxy 가 활성화 시 API 서버의 aggregation 레이어에 특별한 필터 추가 되는데, 이필터는 요청된 리소스가 현재 API 서버가 처리할 수 없는 경우 이를 감지하여 다른 피어 API 서버들로 프록시 요청을 보냄
		- 소스 API 서버가 프록시 대상 피어로 요청을 보낼 때 내부적으로 StarageVersion API를 사용하여 어떤 API 서버가 응답을 제공할 수 있는지 확인하게 되는데 만약 응답이 없으면 503 오류를 반환
		- 프록시가 무한하게 이어지지 않도록 헤더가 사용됨
			- X-kubernetes-APIServer-Rerouted : true 를 설정하여 한 번 리다이렉트된 요청이 다른 피어로 프록시 되지 않도록 제한
	- 내부 흐름
		- 요청이 들어오면 API 서버는 먼저 자신이 해당 리소스를 처리할 수 있는지 자신의 StorageVersion 정보를 이용해 검사
		- 처리가 가능하다면 로컬에서 처리
		- 처리할 수 없는 리소스인데 StorageVersion 객체가 존재하고 피어 API 서버가 리소스를 제공한다면 소스 서버는 그 피어 서버로 요청을  프록시
		- 피어가 없거나(404) 응답이없으면(503) 에러반환
