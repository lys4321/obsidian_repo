쿠버네티스란
- 컨테이너화 된 애플라케이션을 관리하는 오픈소스 플랫폼
- 컨테이너 오케스트레이션 도구

-----
특징
- 서비스 디스커버리와 로드 밸런싱
	- DNS 명이나 자체 IP를 사용해 컨테이너를 노출(디스커버리)
	- 트래픽이 많으면 로드밸런싱 후 배포해 안정적으로 이뤄지게함
- 스토리지 오케스트레이션
	- 저장소 시스템을 자동 탑재
- 자동화된 롤아웃과 롤백
	- 컨테이너 상태를 변경을 이용해 컨테이너 배치 가능
- 자동화된 빈 패킹
	- 사용 리소스를 설정할 수 있는 클러스터 노드를 제공
- 자동화된 복구
	- 실패한 컨테이너에 대한 교체를 자동으로 실행
- 시크릿과 구성관리
	- 컨테이너 이미지를 재구성 하지 않고 시크릿, 애플레이션 구성을 배포 및 업데이트
- 배치 실행
	- 배치, CI 워크로드를 관리하여 실패한 컨테이너에 대한 교체
- 수평 확장
	- 명령어나 자원 사용량에 따라 자동으로 애플리케이션 확장/축소
- 확장성을 고려한 설계
	- 업스트림 소스 코드를 변경하지 않고 클러스터 기능을 추가

컴포넌트
크게 Control Plane과 1개 이상의 Wokrer Node로 구성
- Control Plane
	- CCM(Cloud Controller Manager) 
		- 기본 클라우드 공급자와 통합
	- CM(kube-controller-manager)
		- 컨트롤러를 실행해 k8s API 동작을 구현
	- etcd(persistence store)
		- 모든 API 서버 데이터를 위한 일관성, 고가용성 기능을 갖춘 키-값 저장소
	- api(kube-apiserver)
		- k8s HTTP API를 노출하는 서버 컴포넌트 
	- sched(kube-scheduler)
		- 아직 노드에 할당하지 않은 파드를 찾아 노드에 할당
- Woker Node
	- kubelet 
		- 파드와 그 안의 컨테이너가 실행 중임을 보장
		- CRI를 호출해 컨테이너 런타임 생성
	- kube-proxy
		- 노드에서 네트워크 규칙을 유지하여 서비수 구현
	- 컨테이너 런타임
		- 컨테이너 실행을 담당하는 SW
		- CRI의 구현체

추가적인 구성요소
- 애드온 
	- DNS 
		- 클러스터 전반의 DNS 해석 담당
	- 웹 UI (대시보드)
		- 웹 인터페이스를 통한 클러스터 관리 제공
	- 컨테이너 리소스 모니터링
		- 컨테이너 매트릭을 수집, 저장
	- 클러스터-레벨 로킹
		- 컨테이너 로그를 중앙 로그 저장소에 저장

오브젝트
k8s 오브젝트란?
- '어떤 노드'에서 '어떤 커네이너화 된 애플리케이션' 이 실행중인지
- 해당 애플리케이션에서 사용 가능한 '리소스'
- 재시작 정책이나 업그레이드, 내결함성 같은 애플리케이션의 '동작 방식에 대한 정책'
=> 같은 이런 상황에 처하면 어떤 것을 할 것같다는 '의도의 기록(Record of Intent)'

오브젝트 명세(spec)과 상태(status)
- 명세(spec)는 오브젝트 생성 시, 설정하며 리소스에 원하는 특성에 대한 설명을 제공해야하는데 이를 'desired state'
- 상태(status)는 k8s 시스템과 컴포넌트가 제공하고 업데이트하는 오브젝트의 '현재 상태'

주로 YAML/YML 파일에 명세 내용이 작성되며 필수 필드로는
- apiVersion : 오브젝트를 생성하는데 사용하는 k8s API 버전
- kind : 생성하려는 오브젝트 종류
- metadata : name, UID 및 namespace 등을 포함하여 오브젝트를 고유하게 식별하는데 필요한 데이터
- spec : 오브젝트에 대해 원하는 상태
이 있다.

오브젝트 이름과 ID
- name
	- 리소스 URL에서 오브젝트를 가리키는 클라이언트 제공 문자열
	- 각 시점에 같은 종류에서 하나의 이름은 하나의 오브젝트에만 지정 가능(다른 버전이나 다른 종류에선 같은 이름을 가질 수 있다.)
- UID(UUID)
	- 오브젝트를 중복없이 식별하기 위한 k8s 시스템이 생성하는 문자열
	- 고유하다(마치 DB의 PK)

오브젝트 레이블과 셀렉터
- label
	- 파드,서비스, 디플로이먼트 같은 오브젝트에 첨부된 키-값 쌍
	- 사용자 친화적 데이터를 가짐
	- 오브젝트 하위 집합을 구성하고 선택하는데 사용
	- 오브젝트 생성 시 첨부하며 이후 추가 및 수정이 가능
	- 오브젝트마다 레이블 정의가 가능하며 오브젝트의 키는 고유해야한다.
- selector(레이블 셀렉터)
	- 레이블은 고유하지 않기 때문에 이를 보완하기 위해 사용하는 그룹화 요소
	- 일치성 기준 요건(Equality-based Selector)
		- 일치, 불일치로 레이블 키와 값을 필터링
		- \=, \==, \!= 연산자만 허용
		- 예시 : env = prod   tier != backend
			- prod포함, backend 제외하고 필터링
	- 집합성 기준 요건(Set-based Selector)
		- 집합 여부 기준으로 키와 값을 필터링
		- in, notin, exists(!) 연산자만 지원
		- 예시 : env in (prod, stg)  tier notin (backend, worker)
			- prod, stg 포함, backend, worker 제외하고 필터링
	- 레이블과 셀렉터를 조합해서 사용하는 이유
		- k8s는 파드를 직접 지정하지 않기 때문

오브젝트 네임스페이스
- k8s에서 단일 클러스터 내에서 리소스 그룹을 격리하기위해 사용하는 가상 구획
- 기본 네임스페이스 구성
	- default : 기본으로 설정된 네임스페이스
	- kube-node-lease : 노드 heartbeat 정보를 담는 lease 오브젝트 저장용 네임스페이스
	- kube-public : 읽기전용 리소스 보관 네임스페이스
	- kube-system : 컨트롤러, DNS, kube-proxy 시스템 컴포넌트 전용 네임스페이스
- 핵심기능
	- 리소스 이름 충돌방지
	- RBAC 권한 분리 : 마치 깃에서 브런치를 나누는 것처럼 권한을 적용
	- 리로스 쿼터(Quota) 적용 : 리소스 스펙 제한 가능
	- 네트워크 정책 적용 : 네임스페이스 별로 NetworkPolicy 적용
	- 

오브젝트 어노테이션
- k8s 오브젝트에 임의 메타데이터를 설정하는 방법
- 키-값 쌍 을 가지지만 선택하거나 그룹화하는 용도는 아님
- 도구, 라이브러리, 자동화 시스템이 추가 정보를 남기기 위해 사용
- 변경사항이나 친인간적 데이터 명시
- 예 : metadata : annotations : 키 : 값

오브젝트 필드 셀렉터
- k8s 오브젝트의 특정 필드값으로 리소스를 선택할 수 있는 메커니즘
- 레이블 셀렉터와 달리 오브젝트 메타데이터나 상태 필드로 필터링
- \=, \==, \!= 연산자만 지원하고 조합(AND) 조건(,)으로 필터링 가능
- 레이블과의 차이점
	- 레이블은 오브젝트에 붙이는 메타데이터이지만 필드는 오브젝트 내부 스펙/상태 필드이다
	- 레이블은 그룹핑, 서비스 선택, 컨트롤러 매칭에 목적이 있다면, 필드는 특정 상태/속성 기반 오브젝트 필터링이 목적

오브젝트 파이널라이저
- 오브젝트가 삭제 요청을 받은 후, 실제 삭제되기 전에 특정 조건이 충족될 때까지 대기하도록 지시하는 메타데이터 키
- 사용자의 삭제요청 후, 삭제대기시간이 설정되어도 이 파이널라이즈 필드에 키가 남아있는 경우 종료상태로 남음
- 파이널라이즈는 가비지 컬렉션이나 종속 리소스 처리등의 맥락에서 사용됨
- 이것을 사용하는 이유는 단순히 오브젝트를 삭제하고 완료가 아닌, 오브젝트 삭제전에 이뤄져야할 작업이 있을 때 이것들을 올바르게 작업 후 정상적으로 삭제하기 위해 사용한다.
	- 예시
		- 오브젝트 삭제 시, 해당 오브젝트가 사용하던 persistance Volume가 삭제가 될 수 있어 이를 방지하기 위한 작업실행을 위해 파이널라이저 선언

오브젝트 소유자와 종속자(Owner and Dependents)
- k8s에선 어떤 객체가 다른 객체의 Owner가 될 수 있다는 개념
- 이 관계를 통해 k8s는 리소스의 생애주기 관리나 정리, 의존성 관계 추적을 가능하게 함
- 주요 구성 요소로는 'metadata.ownerReferences'가 있음
- 작성 예시
	- metadata: ownerReferences : \~~~
		- '-' 의 의미 : YAML에서 쓰는 배열항목 의미
		- ownerReferences 하위 필드 종류
			- apiVersion : 소유자 객체의 API버전
			- kind : 소유자 객체 종류
			- name : 소유자 객체명
			- uid : 소유자 객체 UID
			- controller : true면 소유자 객체가 이 종속자를 컨트롤
			- blockOwnerDeletion : true면 종속자가 있을 때 소유자 삭제를 차단
- 해당 개념을 사용하면 이점
	- 리소스 생명주기 일관성 확보
	- 명확한 의존 관계 표현
	- 운영 안정성 강화
	- 컨트롤러 설계의 기반

오브젝트 권장 레이블
- 기능적인건 아니고 k8s에서 권장하는 레이블 구조
- 레이블
	- `app.kubernetes.io/name` : 애플리케이션 이름(예 : mysql)
	- `app.kubernetes.io/instance` : 애플리케이션의 인스턴스 식별 이름(예 : mysql/abcd)
	- `app.kubernetes.io/version` : 애플리케이션의 현재 버전(예 : 5.3.22)
	- `app.kubernetes.io/component` : 아키텍처 내 구성요소(예 : database)
	- `app.kubernetes.io/part-of` : 이 애플리케이션의 전체 이름(예 : wordpress)
	- `app.kubernetes.io/managed-by` : 애플리케이션의 작동을 관리하는데 사용되는 도구명(예 : Helm)

쿠버네티스 API
- 쿠버네티스 API란?
	- kube-apiserver에게 보내는 k8s 오브젝트 상태를 쿼리하고 조작하기 위한 요청
- 사용하는 이유
	- 모든 명령, 상태조회, 리소스 생성은 kube-apiserver를 통해 이뤄지기 때문에 원하는 요청을 보내기 위하여 사용
	- API는 RESTful 구조로 설게되어 HTTP 요청으로 리소스를 CRUD 가능
- API의 구조와 버전
	- k8s API 는 여러 그룹으로 나눠짐
		- core/v1(기본그룹)
		- batch/v1
		- `rbac.authorization.k8s.io/v1` 등
	- 그룹과 버전을 통해 API 경로가 정해진다.(예 : /api/v1, api/v2)
	- 서로 다른 버전이 동일한 리소스의 표현을 제공
		- '서로 다른 버전이 동일한 리소스의 표현' 이란
			- 같은 리소스(예 : Deployment)라도 여러 API 버전(예 : apps/v1beta1, apps/v1) 을 제공
	- API 안정성 수준
		- 안정(stable) : 안정된, 장기 호환성 보장하는 버전
		- 베타(Beta) : 실험적/새기능이 포함된 버전
		- 알파(Alpha) : 심화적으로 실험적인, 진짜 완전 실험적
- 데이터 저장과 직렬화
	- k8s는 오브젝트 상태를 etcd에 저장하는데 API 서버가 여기를 읽고 쓰는 중앙 허브 역할함
	- API 오브젝트는 OpenAPI 스펙을 통해 정의 됨
	- 내부적으론 Protobuf 직렬화 형식을 사용해 클러스터 내부 통신을 효율화
- API 확장성
	- 커스텀 리소스(Custom Resource Definition, CRD)를 통해 사용자 정의 API 타입을 k8s 클러스터에 추가 가능
	- API 애그리게이션(Aggregated API)레이어를 사용해 별도의 API 서버를 연결 가능
- API 접근과 보안
	- API를 사용하기 위해서는 인증과 인가를 거쳐야함
	- k8s는 여러 클라이언트 라이브러리를 제공
	- 파드 내부에서도 API에 접근이 가능(파드 내에서 클러스터 정보를 읽거나 조작할 때 유용)

클러스터 아키텍처
개요
- 클러스터란 k8s를 구성하는 기본 단위로, 여러 노드와 컨트롤 플레인으로 구성됨
- 이것의 목적은 컨테이너화된 애플리케이션을 안정적으로 배포 스케일, 관리하는 것
- 구성 요소
	- 컨트롤 플레인(Control Plane)
		- 클러스터를 관리하고 의도한 상태를 유지하는 중심 컴포넌트
		- kube-apiserver
			- 클러스터의 중앙허브 역할을 담당하고 모든 REST API 요청을 처리
			- 상태를 etcd에 저장하고 인증, 권한 검사를 수행
		- etcd
			- 분산 키-값 저장소이며, 클러스터 상태(오브젝트 상태)를 저장
			- API 서버는 etcd에서 데이터를 읽고 쓰며, 내부 모델 기준으로 버전을 변환
		- kube-scheduler
			- 새로 생성된 파드를 적절한 노드에 배치
			- 리소스 요구량, 정책, affinity/anti-affinity 등 고려
		- kube-controller-manager 
			- 다양한 컨트롤러 실행
			- 예시로 ReplicaSet, Deployment, Node Controller 등 
			- 선언적 상태(desired state)와 실제 상태(actual state)를 맞추는 담당
		- cloud-controller-manager
			- 클라우드 인프라와 연동
			- 노드 상태, 로드밸런서, 볼륨 등을 관리
	- 노드(Node)
		- 애플리케이션이 실제 실행되는 서버 단위
		- kubelet
			- 노드에서 실행되는 에이전트
			- 파드가 정상 실행이 되는지 감시하고 상태를 API 서버에 보고
		- kube-proxy
			- 네트워크 프록시 및 로드밸런싱
			- Service IP와 파드 간 연결 유지
		- 컨테이너 런타임(Container Runtime)
			- 실제 컨테이너를 실행하는 엔진
			- 예 : 도커, containerd, CRI-O
- 클러스터 동작 개념
	- 사용자가 Deployment 생성 요청 -> kube-apiserver
	- API 서버가 상태를 etcd에 기록
	- kube-scheduler가 파드를 노드에 배치
	- kubelet이 노드에서 파드를 실행하고 상태를 보고
	- 컨트롤러 매니저가 실제 상태와 의도한 상태를 비교해서 부족한 파드를 생성하거나 삭제
		- 이 과정에서 Desired State와 Self-healing 개념이 중요

노드
- 노드 란?
	- k8s에서 실제 애플리케이션이 실행되는 곳을 의미
	- 물리 서버, 가상머신 모두 가능
	- 하나의 클러스터에는 여러 노드가 존재 가능하며, 각 노드는 컨테이너화 된 애플리케이션(Pod)을 호스팅
- 노드의 구성 요소
	- kubelet
		- 노드에 항상 실행되는 에이전트
		- 기능
			- 노드에서 Pod가 정상적으로 실행하는지 감시
			- Pod 상태를 API 서버에 보고
			- Pod 스펙에 따라 컨테이너 런타임에 명령 전달
	- 컨테이너 런타임(Container Runtime)
		- 실제 컨테이너를 실행하는 엔진
		- 도커, containerd, CRI-O 등
		- kubelet 이 Pod 스펙을 바탕으로 컨테이너를 관리
	- kube-proxy
		- 네트워킹 및 서비스 라우팅 담당
		- 기능
			- Service IP를 Pod와 연결
			- 로드밸런싱 수행
			- 클러스터 내/외부 트래픽 관리
- 노드 역할 및 기능
	- Pod 실행 : 워커 노드는 컨트롤 플레인에서 스케줄된 Pod를 실행
	- 상태 보고 : kubelet이 Pod와 노드 상태를 API 서버에 주기적으로 보고
	- 네트워크 관리 : kebe-proxy를 통해 Service와 Pod 간 통신 제공
	- 리소스 관리 : 리소스 모니터링 및 컨테이너 할당
컨트롤 플레인 - 노드 간 통신
- k8s 클러스터에선 컨트롤 플레인과 노드 사이에선 지속적인 통신이 이뤄짐
- 목적
	- 컨트롤 플레인이 클러스터 상태를 관리
	- 노드가 Pod 실행 상태를 보고
	- 리소스 상태, 이벤트, 네트워크 정보 등을 전달
- 통신 방향
	- 노드->컨트롤 플레인
		- kubelet이 주도
		- 기능
			- 노드 및 Pod 상태를 컨트롤 플레인에 주기적으로 보고
			- 컨테이너 상태, 이벤트, 노드 리소스 사용량을 전달
			- 컨트롤 플레인에게 Desired State와 Actual State를 비교한 정보를 제공
		- 통신 방식
			- HTTPS 요청을 통해 kube-apiserver와 통신
			- API 서버 인증 및 인가 검사를 거침
	- 컨트롤 플레인->노드
		- 컨트롤 플레인이 주도
		- 기능
			- kube-scheduler가 스케줄링한 Pod 실행 명령을 전달
			- 컨트롤러 매니저가 Pod 관리 명령을 전달
		- 통신 방식
			- API 서버를 통한 kubelet과의 간접 통신
- 통신 구성 요소
	- kubelet : 노드에서 Pod 실행 및 상태를 보고
	- kube-proxy : 네트워크 트래픽 관리, 서비스 라우팅
	- kube-apiserver : 중앙 허브, 모든 요청에 대한 처리 및 상태 기록
		- 통신은 TLS 기반, 인증 및 RBAC 권한 확인 후 처리
	- etcd : 클러스터 상태 저장소
	- Controller Manager : 상태 비교 및 조치 수행
	- Scheduler : 새 Pod 배치 결정
리스(Lease)
- Lease 란?
	- k8s 에서 리소스 상태 유지와 주기적 갱신(heartbeat) 정보를 관리하기 위한 API 오브젝트
	- 주로 Node Lease 형태로 사용되며 노드의 생존상태(node heartbeat) 를 추적하는 용도로 사용
		=> Lease는 컨트롤 플레인이 노드가 살아있는지 확인하는 경량 오브젝트
- 구조
	- Metadata
		- 이름(metadata.name), 네임스페이스(metadata.namespace)
		- Node Lease는 보통 kube-node-lease 네임스페이스에 존재
	- Spec
		- Lease 정보와 갱신 관련 데이터
		- 대표 예시
			- holderIdentity : Lease를 소요한 객체 이름(노드명)
			  leaseDurationSeconds : Lease 유효 기간
			- acquireTime/renewTime : Lease 획득 및 갱신 시간
- 사용 목적
	- node heartbeat 관리
		- kubelet이 주기적으로 갱신
		- 컨트롤 플레인은 갱신 시간을 보고 노드의 생존여부 파악
	- 클러스터 성능 최적화
		- 기존 node status 보다 가볍고 효율적
		- node 상태 확인에 발생하는 etcd 쓰기 부담이 감소
